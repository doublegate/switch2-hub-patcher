# DP-port HDR and VRR: research notes

Status: **research only**. Nothing here is in the patch pipeline. Every register
below comes from the public Realtek tool database for the related **RTD2172**
(`roufsweb/portable-display`, `02_RTDCustomerTool_V3.8/RTDScaler/RTD2172/DB.bin`).
These are working assumptions for the RTD2142 until a real dump confirms them.

One check supports reusing it: the RTD2172 names page `0x5B` "HDMI2.0 Tx MAC0".
The registers that the shipped HDMI patch uses (`5B48`, `5B49`, `5B4B`, `5B6B`)
are its `DATA_ISLAND_PACKETIZER_19/20/22/54`. That matches what the patch does to
them: AVI payload bytes, the checksum, and a packet enable. The upstream author
also reports that the database's names matched the RTD2142 firmware.

XDATA address = page << 8 | register (`0x4DB6` = page 0x4D, register 0xB6).

## 1. HDR on the DisplayPort output

**Symptom:** HDR through the hub's DP port is washed out or not offered. The same
mechanism caused the HDMI bug: the Switch 2 sends PQ/HLG metadata but does not
mark the stream as BT.2020, so the monitor falls back to BT.709 primaries.

**DP 1.4 fix:** send the colorimetry in a VSC SDP (revision 05h). Set MSA MISC1
bit 6 so the sink ignores MSA colorimetry. Only do this when the sink advertises
DPCD `0x2210` bit 3 (VSC SDP colorimetry supported).

### Registers (RTD2172 DP 1.2 TX0, pages 4D/4E; TX1 is BB/BC at the same offsets)

| Addr | Name | Use |
| --- | --- | --- |
| 4DB4 | MSA_CTRL | bit 7 `msa_db`: latch new MSA values |
| 4DB5 | MSA_MISC0 | [7:5] bpc, [4] BT.601/709, [3] CEA range, [2:1] RGB/422/444 |
| 4DB6 | MN_STRM_ATTR_MISC1 | bit 6 `pixel_fmt_indi`: colorimetry is in the VSC SDP |
| 4E00 | SEC_FUNCTION_CTRL | bit 2 `psr_en`: transmit VSC SDP; bit 4 AVI; bit 7 reserved-infoframe slot 0 |
| 4E02 | SEC_DBUF_CTRL | bit 0 `sec_db`: latch SDP header/payload; bit 1: latch at vblank |
| 4E04–4E13 | SEC_PSR_DB0–15 | VSC payload |
| 4E14 | SEC_PSR_DB16 | [7:4] pixel encoding, [3:0] colorimetry (6 = BT.2020) |
| 4E15 | SEC_PSR_DB17 | [7] CEA range, [2:0] bpc |
| 4E16 | SEC_PSR_DB18 | content type |
| 4E26–4E2B, 4E53–4E56 | DP_INFO_FM_RSV0..2 | reserved SDP slots (HB2/HB3, type, payload port). These are the likely carrier for the HDR static-metadata SDP (type 87h) |

### Draft

`research/dp_hdr_vsc.asm` (98 bytes; assembles with SDCC 4.6.0, but it is neither
hooked nor flashable). It is the DP twin of `asm/rtd2142_hdr_avi.asm`. When the
caller sets C=1, it writes DB16/17/18 from the stream's MISC0, sets MISC1 bit 6,
enables VSC transmission and latches at vblank. C=0 restores SDR signalling.

### Findings from the stock dump (2026-11-14)

From the stock dump (`17eea728…d802`), read with Ghidra 12 (see
[Tools](#4-tools-ghidra-and-the-symbol-map)). Function names are from
`research/rtd2142_symbols.tsv`; `_q` marks a role inferred from one use site.

- **The DP output is TX1.** `survey` finds 31 references to `BBxx/BCxx` and none to
  `4Dxx/4Exx`, so the register table above applies at `BB`/`BC`.
- **The firmware already has a VSC colorimetry path.** `dptx1_program_msa` (bank 2
  `AFC4`, called after timing setup) and `dptx1_update_colorimetry` (bank 2 `9E7D`)
  first program MISC0/MISC1 (`dptx1_program_msa_misc`, `977E`), then:
  - if the TX colorimetry index `DF2F[6:3]` is `0x0D` and `DF25` bit 6 is set, they
    build the VSC payload (bank 1 `91F2`, from the pixel format `DF2D` and the
    extended-colorimetry index `DF2E`), write the VSC header (bank 1 `9FCD`, type 7),
    set `SEC_FUNCTION_CTRL` (`BC00`) bit 7 and set MISC1 bit 6;
  - otherwise they clear MISC1 bit 6 and send no VSC colorimetry.
- **The VSC header is generated by firmware, not hardware.** `dptx_sdp_header`
  (bank 1 `9FCD`) writes HB0–HB3 to `BC73`–`BC76` and selects the header slot in
  `BC7B`. For type 7 it writes HB2/HB3 = `05h`/`13h` (DP 1.4 VSC revision 5,
  19 bytes) when the index is `0x0D`, and `01h`/`01h` otherwise. Payloads go through
  a port: address `BC8B`, data `BC8C`, slot `BC8D[2:0]` (`dptx_sdp_payload`, bank 1
  `BC9D`). The `SEC_PSR_DB` registers (`BC04`–`BC16`) are never addressed directly.
- **HDR metadata is already forwarded on the DP port.** `dptx_sdp_header` type `0x0D`
  builds an SDP of type `87h` (HDR static metadata), and `dptx1_update_sdp_enables`
  (bank 2 `9CD8`) drives `BC00` bit 5 from it. That fits the symptom: the monitor
  gets PQ metadata, but no BT.2020 colorimetry, so the picture is washed out.
- **The index 0x0D is most likely Realtek's "extended colorimetry"** (BT.2020 and
  similar, with the detail in `DF2E`). Upstream reports that the converter "only
  takes BT.2020 from the incoming DP stream when it is signalled in one specific
  standard way", which matches this gate. Not confirmed from Realtek sources.

**Revised plan for the DP-port patch.** Hook the colorimetry gate in both callers
(bank 2 `B0BC` and `9FDC`) so the existing path also runs while PQ/HLG metadata is
present, with `DF2E` set to BT.2020. That reuses the firmware's own VSC header,
payload and latching instead of the standalone draft. Still to find: the DP port's
"HDR active" flag (the HDMI patch reads `E362` bit 1 / `DD9F` for logical port 1),
and whether `DF25` bit 6 is the downstream DPCD `0x2210` bit 3 flag.

## 2. VRR

### Context

- Switch 2 system update **23.0.0 (September 2026)** added VRR in TV mode. It also
  needs a **dock firmware update** on the official dock (Settings > System > Dock
  Update), and games must opt in (at launch only *Welcome Tour* 1.1.0 did).
- The patched hub answers the version queries with records copied from the
  official dock, so the console offers VRR. Upstream saw the DP output freeze and
  HDMI stay at 60 Hz. Keep **VRR off**, and **never accept a Dock Update** with
  the patched hub: there is no update handler, and nothing about that path has
  been tested.

### Why it fails: the receiver regenerates timing

The RTD2172's DP RX has a per-stream display-format generator (DPF) that
rebuilds HSYNC/VSYNC. It runs in `frame_sync_mode` (or "full last line"). With a
variable vblank, the regenerated timing and clock tracking have to re-lock every
frame, which is the "clock re-lock loop" upstream suspected.

The silicon does have a VRR mode:

| Addr (stream 1; ST2 B3xx, ST3 B5xx, ST4 B8xx) | Name | Field |
| --- | --- | --- |
| B130 | DPF_CTRL_0 | bit 5 `frame_sync_mode`, bit 4 `deonly_mode` |
| B190 | DP_RSV0 | bit 0 `drr_mode`: VS just before the first DE line |
| B191 | DP_RSV1 | bit 7 `deonly_full_mode` (after FIFO/tracking stable), bit 6 `de_window_fix_en` |
| B19A | DP_RSVA | bit 0 `vrr_mode`: "if vrr mode & deonly mode, DPF uses the Adaptive-Sync SDP to generate VS"; bit 1 `vrr_vs_mode` |
| B2FC | DUMMY_2 | bit 0 `vsc_for_vrr_en`: pass received Adaptive-Sync info to the DPF instead of filtering it |

So the "rewrite of the input lock" probably reduces to enabling the hardware
mode: `deonly_mode` + `vrr_mode` (+ `vsc_for_vrr_en`, and possibly
`deonly_full_mode` once tracking is stable). This applies only while the source
actually sends Adaptive-Sync SDPs, and the upstream DPCD must advertise
Adaptive-Sync (`MSA_TIMING_PAR_IGNORED`, DPCD 0x0007 bit 6) so the Switch varies
the timing.

### Findings from the stock dump (VRR, 2026-11-14)

With the full RTD2172 register database applied to every bank (see section 4):

- **Stream 1 runs in full-last-line mode, not frame-sync.** `dprx1_program_dpf_timing`
  (bank 6 `9EDA`) turns the DPF off (`DPF_CTRL_0.disp_en` = 0, `MAC_DIG_RESET_CTRL`
  `dpf_reset`), programs the regenerated timing from the received MSA
  (`MN_DPF_HTT`…`MN_DPF_VSW`, `B141`–`B150`) and the frame-sync offsets
  (`EVBLK2VS`/`OVBLK2VS`, `B133`–`B137`), then clears `frame_sync_mode` and
  `deonly_mode` (`B130 &= 0x4F`). The only `B130` bit any stream-1 code sets directly is
  `disp_en` (`set_bit7_at_dptr`). In full-last-line mode the DPF generates Vtotal
  lines and stretches the last one; a varying vblank breaks that every frame, the
  video FIFO over- or underflows (`PG_CTRL_1`, `B121`) and the video watchdog blanks
  the output. That fits upstream's black screen.
- **The hardware VRR mode is never used.** Nothing addresses `DP_RSVA` (`vrr_mode`,
  `vrr_vs_mode`) or `DUMMY_2.vsc_for_vrr_en` for any stream (`B19A/B39A/B59A/B89A`,
  `B2FC/B4FC/B6FC/B9FC`). The database states the priority:
  `vrr_mode` with `deonly_mode` > `deonly_mode` > frame-sync / full last line, and the
  order "deonly_mode, disp_en, then deonly_full_mode after FIFO and tracking are
  stable". With `vsc_for_vrr_en` clear the receiver filters Adaptive-Sync SDPs
  (type `22h`) out before they reach the DPF.
- **The Adaptive-Sync advertisement is not in a ROM table.** The receiver DPCD is
  reached through a port (`DPCD_ADDR_PORT_H/M/L` `B7C1`–`B7C3`, data `B7C4`; helpers
  `dpcd_set_addr*`). No code loads address `00:00:07` as immediates and no DPCD
  capability table exists in the banks, so `MSA_TIMING_PAR_IGNORED` (DPCD `0x0007`
  bit 6) is either a hardware default or written through a computed address. In an
  MST topology the last branch device must set this bit itself for the source to
  use Adaptive-Sync, so it is required, not optional.
- **Answered live (2026-11-14): stream 2 carries the hub's input.** `rtd-peek B130
  B330 B530 B830` reads `00 80 00 00`: only stream 2's display enable is set, with
  the mode bits clear (full-last-line). Its code is in bank 5 and mirrors stream 1:
  `dprx2_program_dpf_timing` (bank 5 `92F2`, called from `rx2_stream_setup` at
  `D7EC`) clears `disp_en` at `931F` and selects full-last-line at **`94CC`**
  (`B330 &= 0x4F`). The VRR hook belongs there, not at bank 6 `A0BC`.

So "VRR on" for the DP port is, in order: advertise `MSA_TIMING_PAR_IGNORED`; while
the source sends Adaptive-Sync SDPs, set `vsc_for_vrr_en`, `deonly_mode` and
`vrr_mode` (instead of full-last-line) before `disp_en`, then `deonly_full_mode` once
stable; and keep the DP TX timing in step (its MSA comes from the same
`DF04`–`DF14` copy). The hook is the end of `dprx1_program_dpf_timing`
(bank 6 `A0BC`, the `B130 &= 0x4F`) for whichever stream is live.

### Per output

- **DP port:** the most plausible target. With the DPF in VRR mode and the TX
  forwarding the Adaptive-Sync SDP (it has the reserved SDP slots above), a
  FreeSync/Adaptive-Sync DP monitor could follow. Upstream's attempt
  (Adaptive-Sync advertisement plus EDID override) failed because the DPF stayed
  in frame-sync mode.
- **HDMI port:** much harder. Besides varying timing, the HDMI TX must send either
  an HDMI 2.1 VRR EMP (VTEM) or AMD's FreeSync-over-HDMI vendor InfoFrame
  (OUI 00001A). The RTD2172 database has no named EMP/VRR registers on the HDMI
  2.0 TX, only generic data-island packet slots. A FreeSync VSIF through a
  generic InfoFrame slot is the realistic option. It is unknown which signal the
  official dock uses.

### What the official dock does differently (findings, 2026-11-14)

- **The fix is RTD2142 firmware, not VL103.** The console side already works: the
  VL103 version replies make the Switch offer VRR and send variable timing. Both
  failures (DP freeze/black on varying frame rate, HDMI stuck at 60 Hz) are in the
  converter: the DPF cannot follow a variable vblank, and the HDMI TX never sends
  a VRR packet.
- **The official dock's converter is a different, HDMI 2.1-class part.** Switchbrew
  lists its DP-to-HDMI converter as a Realtek **RTD2175N**, and press coverage of
  the pre-23.0.0 limitation describes it as a DP 1.4 to HDMI 2.1 converter.
  Third-party tests found the official dock already passes VRR to a TV when a PC
  or another handheld is the source. So the official "Dock Update" mostly unlocks
  a capability that converter already had. The RTD2142 is a lower-tier converter
  with an HDMI 2.0 TX, and whether it can follow variable timing at all is unproven.
- **Live register access is the missing tool.** Upstream read and wrote live RTD2142
  registers through a firmware debug interface at I²C address **0x35** over the
  same AUX channel, without flashing. Its protocol is not published, and this
  repository's `rtdisp.py` implements only the ISP interface at 0x4A. Recovering it
  from a stock dump turns the VRR work into volatile register pokes that a power
  cycle undoes, instead of flash-and-test iterations.
- **Value is limited.** At 23.0.0 only *Welcome Tour* 1.1.0 used docked VRR.
- **Do not suppress VRR from the VL103 side.** Replaying an older dock version to
  stop the console offering VRR risks a Dock Update prompt, and the patched hub has
  no update handler. A safer interim change, if wanted, is an RTD2142 patch that
  hides the TV's VRR capability (EDID range / DPCD 0x0007 bit 6) from the console,
  so it never offers VRR. That is simpler than VRR itself but needs the same
  RTD2142 access.

1. **Reach the RTD2142.** It is flashed over the hub's DP input, not USB. A desktop

   branch. Use a Linux laptop with an Intel/AMD iGPU and a USB-C DP-alt-mode port,

   macOS: stock dump `17eea728…d802`.*
2. **Land the shipped RTD2142 HDR step first.** It is the same chip and write path.
   *Flashed 2026-11-14: HDR from a Mac looked right, but a Switch 2 gave no picture,
   so the hub went back to stock. Live reads then found the stock HDR-to-SDR bugs
   (section 5). Revised order:*
   1. *SDR-fix v2 (`d249fa20…a695`): flash it and verify (Mac HDR/SDR switching with
      a recording, Switch 2 SDR/HDR from a cold plug-in).*
   2. *Re-verify the BT.2020 patch against what is known now (done on paper: right
      bytes and checksum; it self-corrects after an output restart on the next

   3. *Then VRR (steps 3 to 7 below), on top of whichever image proves stable.*

## 3. The 0x35 debug interface

Upstream used a firmware debug interface at I²C address **0x35** (8-bit `0x6A`),
reached over the same DP AUX channel as the ISP at `0x4A`, to read and write live
registers. Its protocol is not published. Decoded from the stock dump and **confirmed on
a chip on 2026-11-14** (reads, and single-byte writes through `rtd-clear-bits`):

- **Setup:** `dbg_i2c_slave_init` (bank 0 `E674`) writes `0x6A` to the slave-address
  register `FF23` and enables external interrupt 1.
- **Receive:** `dbg_i2c_slave_isr` (bank 0 `9B74`) takes the first byte of an I²C
  write (the sub-address, `FF24`) as the command (`E28B`) and buffers up to 32 data
  bytes from `FF25` into `E28C…`. At the stop condition it flags the command for the
  main loop. A read from 0x35 returns `FF26`.
- **Session:** command `0x55` (with data `00`) enters debug mode
  (`dbg_service`, `2972`); `0x2F` leaves it. Non-zero `0x55` data bytes set a filter
  (`E268`/`E269`) whose meaning is not decoded.
- **Dispatch:** `dbg_dispatch` (`2C4D`) switches on the command through Keil's
  `?C?CCASE` table at `2C5F`:

| Command | Handler | Effect |
| --- | --- | --- |
| `0x3A` | `2D11` | read XDATA[`E28D`:data byte] into `FF26` |
| `0x3B` | `2D24` | write `E28E` to XDATA[`E28D`:data byte] |
| `0xBB` | `309A` | block read: address, length ≤ 24, auto-increment, 8-bit checksum |
| `0xBA` | `32FB` | block write, same header; status `00` OK, `E1` length, `E2` checksum |
| other, low nibble 1 or 2 | `2D59` | data byte → `E28D` (address high byte) |
| other, low nibble 3 or 6 | `2D59` | data byte → `E28E` (byte for `0x3B`) |
| other, low nibble 5 | `2D59` | data byte → `E28F` (auto-increment) |
| `0x2F` | `2CE9` | leave debug mode |
| `0x41`, `0x44`, `0x45`, `0x80`, `0x7A`, `0xC9`, `0xCA` | various | not decoded |

So a single-register read is expected to be: write `[0x55, 0x00]`; write
`[0x01, addr_hi]`; write `[0x3A, addr_lo]`; read one byte; finally write `[0x2F, 0x00]`
(commands run only with at least one data byte).
Registers are XDATA addresses, the same space as the `survey` register names.
Reads in debug mode change no flash, and a power cycle leaves debug mode.

**`rtd-peek`** (`switch2_hub_patcher/rtddbg.py`, tested against the simulated slave in
`tests/fake_dbg.py`) implements exactly these four commands and nothing that writes.
Every run first reads `FF23`, which must return `0x6A`; otherwise it reports nothing.
First live run, with the hub connected and nothing else using it:

```sh
switch2-hub-patcher rtd-peek FF23 B130 B330 B530 B830 B19A B2FC
```

On the chip: the self-check reads `FF23 = 0x6A`, about 150 registers take 4.6 s,
a loop over six registers samples about 6 times a second, and the picture keeps
running. While the firmware restarts the output (a mode switch), some
replies are stale (the previous byte repeated); steady-state reads agree across runs.

**`rtd-clear-bits ADDR MASK --volatile-ram-write`** is the only write: it clears
allow-listed bits (`rtddbg.CLEARABLE`: `E362` bit 1 and `5B07[7:4]`) with
`[0x01, hi]`, `[0x03, value]`, `[0x3B, lo]`, reading before and after. The `0x03`
(low nibble 3 → `E28E`) and `0x3B` handlers were re-checked in the dispatch table
before the first write. It never touches flash; unplugging the hub restores RAM.

Still unknown: the undecoded gate in `dbg_service` (a check through `2074` before
dispatch); it has not rejected any request so far.

## 4. Tools: Ghidra and the symbol map

The firmware is eight 64 KiB 8051 code banks (banks 8–31 are erased). Each bank is
a complete code image: the first 8 KiB are identical in every bank, and calls
between banks go through stubs (`MOV DPTR,#target; LJMP bank_callN`, at
`0x0CB8 + 0x12·N`) that write the bank number to XDATA `FFFF` (`bank_selectN` at
`0x32N0`).

```sh
G=/opt/homebrew/opt/ghidra/libexec/support/analyzeHeadless   # Ghidra 12, 8051 module
python3 -c "import sys;d=open('rtd2142-stock.bin','rb').read();[open(f'bank{b}.bin','wb').write(d[b<<16:(b+1)<<16]) for b in range(8)]"
$G proj rtd -import bank2.bin -loader BinaryLoader -processor 8051:BE:16:default \
   -scriptPath research/ghidra -preScript SeedFunctions.java
$G proj rtd -process bank2.bin -noanalysis -scriptPath research/ghidra \
   -postScript RenameSymbols.java 2 research/rtd2142_symbols.tsv
$G proj rtd -process bank2.bin -noanalysis -scriptPath research/ghidra \
   -postScript DecompSites.java out.txt AFC4 9E7D
```

- `SeedFunctions.java` creates functions at the reset/interrupt vectors and every
  in-bank `LCALL`/`LJMP` target (a raw image has no entry points for auto-analysis).
- `RenameSymbols.java` applies `rtd2142_symbols.tsv` (and any extra TSV, such as one
  generated from `rtd2142_map.REGISTERS`) to the bank. Add names there as roles
  become clear, so every later decompile reads with them.
- `DecompSites.java` decompiles the functions containing the given addresses and
  lists their callers; `Listing.java` prints raw disassembly for address ranges.
- Whole firmware: `auto_names.py stubs` lists the 752 cross-bank entry points (from the
  common-area `MOV DPTR,#target; LJMP bank_callN` stubs). `FunctionReport.java` creates
  functions there and reports every function's size, callers, callees and XDATA reads and
  writes. `auto_names.py names` names default (`FUN_*`) functions by subsystem: the
  register page they touch (from the RTD2172 register names), else by majority over
  callers and callees (6 rounds, across banks). The result is `<sub>_XXXX`,
  `<sub>_ctl_XXXX`, `<sub>_ram_XXXX`, `call_bN_XXXX` or `fn_XXXX`. `DecompileAll.java`
  writes every function. On the stock image: 11,257 functions, all decompiled; 1,174
  named from hardware access, 6,931 by propagation, 1,307 left as `fn_`. Confirmed names
  from `rtd2142_symbols.tsv` are applied after the auto names, so they always win. Keep
  the outputs in `firmware/analysis/` (gitignored, vendor-derived).
- Keep bank images and Ghidra projects outside the repository: they contain vendor
  code. The scripts and the symbol map contain addresses and names only.

## 5. HDR to SDR: the re-detect loop (stock firmware, 2026-11-14)

**Symptom.** Mac (Apple silicon, macOS) → hub → HDMI TV, stock RTD2142. Switching the
Mac from HDR to SDR while connected often leaves the TV cycling between SDR, HDR and
HLG; switching back and forth or replugging the hub ends it. Mac → TV directly over
HDMI is solid in both modes. With the BT.2020 patch the same happens. A fresh plug-in
straight into SDR is stable.

**What the Mac sends (from its IORegistry, `dispext0` colour modes).** HDR: 4K60
YCbCr 4:2:2 12-bit BT.2020 PQ, colorimetry in the VSC SDP (MSA MISC1 bit 6 set). SDR:
4K60 YCbCr 4:4:4 8-bit BT.709 in MSA MISC0 (MISC1 bit 6 clear). Both are 594 MHz on
HDMI. In SDR the Mac keeps sending an all-zero HDR metadata SDP (EOTF 0); the hub
forwards it, but that is the same in the stable and the cycling state, so it is not
the cause. (CTA-861-H wants a source to send that zero packet for 2 s and then stop:
<https://ratatoskr.run/intel-gfx/2026/09/17491615/t>.)

**Live reads, cycling vs stable SDR** (stream 2 is the hub's input: `B330` display
enable is the only one set):

| Register | Cycling | Stable | Meaning |
| --- | --- | --- | --- |
| `B403` MISC1 | `00` | `00` | bit 6 clear: MISC0 is authoritative (DP 1.4a Table 2-96) |
| `B402` MISC0 | `3C` | `3C` | 8-bit YCbCr 4:4:4, BT.709, CTA range |
| `B446`/`B447` VSC | `27`/`83` | (not read) | the last HDR VSC SDP: 4:2:2, BT.2020, 12-bit |
| `DE12` `rx2_fmt_colorimetry` | `7E` | | `[7:4]` = 7 kept from the VSC SDP |
| `E3E6` `rx2_colorimetry_code` | `6E` | | code `0E` = BT.2020 YCbCr |
| `E0E7` `hdmi_in_colorimetry_q` | `8E` | `80` | the HDMI side's copy (field 8) |
| `5B07` HDMI `dp_color_depth` | `60` | `00` | 12-bit depth left over |
| `E09D` | `D0` | `00` | not decoded |

**Mechanism.**

- `rx2_capture_format` (bank 5 `DCF4`) takes the VSC path when MISC1 bit 6 is set
  (sets flag bit `0x2E`, stores the VSC colorimetry in `DE12[7:4]` via `5027`), and the
  MISC0 path otherwise (clears `0x2E`; `508d` updates only `DE12[3:0]`).
- `rx2_colorimetry_from_vsc` (`C37B`) turns YCbCr + `DE12[7:4]` into code 7 + n:
  BT.2020 YCbCr (7) becomes `0x0E`. The HDMI AVI builder (bank 2, `7E17` switch, case
  `7E87`) maps `0x0E` to C = 3, EC = 6: BT.2020.
- During the HDR → SDR switch the format is captured while MISC1 bit 6 is still set.
  Afterwards `rx2_format_matches_q` (`C476`, polled through the stream-good check
  `EF1A`) compares only the pixel encoding when bit 6 is clear (4:4:4 both times), so
  it never reports a change and nothing re-captures. The AVI keeps saying BT.2020 YCbCr
  over BT.709 video while the HDR metadata says SDR gamma; the TV keeps re-detecting.
- Separately, `hdmi_set_deep_color` (bank 2 `E8FF`) writes `5B07[7:4]` only for 10/12-bit
  input; its 8-bit branch (`E952`) never clears it. Clearing it live
  (`rtd-clear-bits 5B07 F0`) did not stop the loop, so it is not the main cause, but a
  fresh start has 0 there.

**Candidate v1** (`f191da0f…8e92`, flashed 2026-11-14): the `C476` hook returned
C = 0 when MISC1 bit 6 was clear and flag `0x2E` was set, plus the `5B07` fix below.
On the hub the colour depth fix worked on every switch (`5B07` back to `00` in SDR, `60`
in HDR), but the TV still cycled on some switches, with E3E6 still `6E`. The reason:
**only `rx2_colorimetry_from_vsc` ever writes E3E6[4:0]**. The MISC0 path
(`rx2_colorimetry_from_misc0`, `D284`) writes E3E7[6:3], and the other E3E6 writers
(bank 5 `E938`/`E94F`) touch bits 6:5 only. So a re-capture cannot clear the code;
only a power-up does. Stable and cycling SDR then read the same in 502 registers, which
points at the contradictory signalling (an AVI saying BT.2020 with an SDR-gamma HDR
packet; displays label "BT.2020 + SDR gamma" as HLG:
<https://discourse.osmc.tv/t/sdr-bt2020-tagged-as-hlg/95144>) rather than the link.

**Candidate v2** (`patch_rtd2142_sdr_fix.py`, `rtd2142 --sdr-fix`, output
`d249fa20…a695`, 48 bytes; 4 sectors from stock, 1 sector, `0x05F000`, from v1):

- bank 5 `C476` → `rx2_fmt_check` (`FD80`): with MISC1 bit 6 clear, a non-zero
  E3E6[4:0] can only be left over from the VSC SDP. Clear it (the power-up value) and
  return C = 0 ("format changed"), so the firmware's own setup (`rx2_stream_setup`,
  `D7BC`) rebuilds the output from MISC0. After that the condition is false and the
  stock check runs. No dependency on flag `0x2E`.
- bank 2 `E952` → `hdmi_deep_color_off` (`FF00`): the stock `5B06 &= FC`, plus
  `5B07 &= 0F` (unchanged from v1).

Not yet run on a hub. To test: flash it (from v1 or stock), switch the Mac HDR → SDR
several times (expect one brief re-sync, then E3E6 / E0E7 `60`/`80` and a stable SDR
picture), and test the Switch 2 with HDR on and off.

**Candidate v2 on the hub, automated soak (2026-11-14).** macOS HDR can be switched
from a script through the private SkyLight calls behind System Settings
(`SLSDisplaySetHDRModeEnabled(display, enabled, 0, 0)`; `SLSDisplayIsHDRModeEnabled`),
so a soak flips HDR every 20 s while the debug interface records the hub:

| Path | Switches | Clean | Failures |
| --- | --- | --- | --- |
| Mac → TV directly (HDMI) | 18 | 18, all under 1 s | none |
| Mac → hub (v2) → TV | 18 | 9 | 4 SDR re-detect loops, 5 HDR "no signal" (3 recovered after 2–3 s) |

- v2 does what it was built for on every switch: SDR always ends with E3E6/E0E7
  `60`/`80` and `5B07` `00`, HDR with `6E`/`8E` and `60`.
- The HDMI 2.0 scrambling check (`hdmi_scdc_scramble_check`, bank 2 `C3EA`) retried
  heavily in the first two minutes (E0AD up to 6, E0D7 bit 4: 10 s re-checks), but
  it does not track the failures: switches 3 and 5 were good while it retried, and
  failures 10 and 13–17 happened with E0D9 = 1 (scrambling locked) throughout.
- Every hub-side register sampled (colour, depth, scrambling, packet enables, FIFO
  `5B02`, EDID `E09D`) ends identical for good and bad switches, and each switch is a
  single 1.5–2 s output restart. Over DP the Mac changes the pixel format on every
  toggle (4:2:2 12-bit ↔ 4:4:4 8-bit), so the hub always restarts its HDMI output;
  directly, the switch takes under a second. The remaining failures are inside the
  restart sequence, faster than 3 samples per second shows. Next: a fast capture of
  the restart registers (`5B08`, `5B6B`, `B330`, `E0D9`, `5A0x`) at about 15–20 Hz,
  good vs failing restarts.

**Fast capture and candidate v3.** A second soak sampled the restart registers
(`5B08`, `B330`, `5B6B`, `E0D9`, `5A04`) at about 6 Hz. The TV was good on 12 of 18
switches; there were 3 SDR loops and 3 HDR "no signal" (2.5, 2.5 and 7 s). The good and
bad restarts look the same at that rate. In the 7 s case the hub had scrambling
locked and everything enabled after about 2 s.

The remaining SDR loops fit a race. The HDMI side reads the colorimetry code
(format field 8, `rx2_get_format_field` `DE88`, case `DEE9` = E3E6 & 1F) and builds
the AVI during its own restart, which can be before v2's polled check clears the
stale code. v3 (`f5de8f43…2b8b`) redirects the field-8 entry of the jump table (`DEAD`)
to `rx2_field8` (`FD9B`), which returns 0 while MISC1 bit 6 is clear, whatever E3E6
holds. It keeps v2's `C476` hook to rebuild an AVI already built during the transition,
and the `5B07` fix.

The HDR "no signal" delays are not addressed. If they remain, check the TV's per-input
HDMI mode and port first: other TVs fail HDR this way, though here direct HDMI on the same
port was clean. Then look at the restart's TMDS/scrambling sequence.

**Per-display quirks and the scrambling check (v4).** A raw-image scan found a
per-display quirk table in bank 2 (`3C87`–`3D36`: EDID monitor-name descriptors such as
"LEN Y27gq-25", "XB273K", "H277HU", "QD980 HDMI", and EDID fragments).
`hdmi_sink_quirks_identify` (`7232`) matches the sink's EDID against it and sets flag bits
in E10B/E10C. This TV matches none (E10B `00`). E10B bit 3 makes `hdmi_scdc_scramble_start`
(`E211`) wait 500 ms instead of 100 ms after writing TMDS_Config, before
`hdmi_scdc_scramble_check` reads the sink's Scrambling_Status (SCDC 0x21).

- Soak A, v3 with E10B `00` (18 switches): 7 switches had status-check retries. The
  user saw the TV run much smoother than on v2 (2 SDR loops and 1 no-signal seen).
- Soak B, v3 with E10B bit 3 set through `rtd-set-bits` (a RAM write; a replug clears
  it). After 6 switches the TV stayed at "no signal": 5B08 `D1` (scramble_en off),
  E0D9 `02`, E0AD `06`, E0D7 `30`. The hub had failed the check four times in about 2 s.
  `hdmi_state_running_q` (`C6D0`) then re-entered setup at E0AD = 6 with E0D7 bit 4 (a
  10 s re-check), and the restart sets HDMI mode with scrambling off
  (`hdmi_mode_unscrambled`, `4AD2`). At 594 MHz that means no picture. The first soak's
  stuck no-signal (12:33:51) has the same signature. One run only, but the TV not
  reporting the bit even with 500 ms waits suggests an unreliable sink status rather
  than timing. The Linux SCDC helper also notes displays that refuse the bit.
- v4 changes one byte: `C432` JZ → SJMP, so the check always takes `hdmi_scdc_status_ok`.
  The trade-off: no in-place recovery if the TV loses scrambling without a hot plug. A
  TV power cycle, input switch or cable glitch normally raises HPD, which reruns the
  full SCDC setup. To verify: soak v4, then power-cycle the TV and switch its input
  away and back without replugging the hub. If that fails, the alternative (v4b) keeps
  the re-checks and rewrites but never falls back to unscrambled output.

**The BT.2020 patch (`rtd2142_hdr_avi`) and this bug.** Its AVI rebuild hooks fire only
when the HDR packet's enable bit changes, but an output restart enables every packet
at once (`hdmi_pkt_enable_all`, `CDAA`), and the AVI is built before the new HDR
metadata (`rx_drm_eotf_p1`, `DD9F`) is current. A rework should decide BT.2020 from
the EOTF on every `hdmi_drm_update` pass. With it flashed, a Switch 2 gave no HDMI
picture (HDR on or off). On SDR-fix v1, which has no BT.2020 change, the same Switch 2
worked in SDR and HDR. The first connection needed several replugs and SDR/HDR toggles,
then it was stable, and the next replug came up at once. That points at the BT.2020
overlay (or its interaction with the Switch's signalling) for the no-picture result.
Not yet explained in the code; the patch should not be used until it is.
